# 2026.321.0714 — feat(virtualization): add a libvirt-group prerequisite candy, ordered ahead of the stack

## Summary

Adds a **`libvirt-group` prerequisite candy** and orders it ahead of `virtualization`, so the `libvirt` group
exists before any libvirt package is configured.

Head `ba0bda7`, **1 file, 28 insertions(+)**.

### Why

On Ubuntu 26.04 (resolute) installing the stack writes a fatal into the package log:

```
Setting up libvirt-daemon-system (12.0.0-1ubuntu5.6) ...
Creating group 'libvirt-qemu' with GID 64055.
Creating user 'libvirt-qemu' (libvirt QEMU user) with UID 64055 and GID 64055.
fatal: The group `libvirt' does not exist.
```

`libvirt-daemon-system`'s maintainer script adds the `libvirt-qemu` user to the **`libvirt` group before it
creates that group**. The group exists moments later, the install exits 0, and every service works — but the
line is there, and a `disposable: true` check bed's `deploy-add` gate rightly refuses to ignore a `fatal:`.

### Measured — and my first fix was wrong

Both directions run in a disposable `ubuntu:26.04` container:

**1. Reorder the packages** (`libvirt-daemon-system` in its own transaction first):

```
$ apt-get install -y libvirt-daemon-system          # fatal lines: 1   <- it MOVED here
$ apt-get install -y libvirt-daemon-driver-qemu …   # fatal lines: 0
$ getent group libvirt
libvirt:x:985:
```

Reordering cannot help: the line belongs to whichever transaction configures `libvirt-daemon-system`, not to
the driver. I had asserted the opposite on opencharly/distro-ubuntu#66 and corrected it there.

**2. Pre-create the group, then install:**

```
$ groupadd -r libvirt && apt-get install -y libvirt-daemon-system
fatal lines: 0
```

That is the fix.

### Why a separate candy rather than a plan step in `virtualization`

Charly emits a candy's declarative `distro:` packages as a `RUN apt-get install …` **before** any `plan:`
step — confirmed in the generated Containerfile (the apt `RUN` at 40-42, the first plan `RUN mkdir` at 65). A
plan step inside `virtualization` would therefore run too late. Candies compose in `require:` order, so a
**prerequisite candy's plan runs before `virtualization`'s packages** — the only declarative way to express
"this group must exist first".

The candy ships no packages and no services; it exists to be ordered. The step is idempotent
(`getent group libvirt || groupadd -r libvirt`) and harmless on Fedora/Arch where the group already exists.
Because a candy needs an agentless assertion (ADE), it carries a `check:` that `getent group libvirt`
succeeds — so the candy's own plan proves what it exists to do.

**The ORDERING, shown in a generated two-candy image rather than asserted.** A throwaway project composing
`libvirt-group` + `virtualization` on `ubuntu:26.04`, generated with `charly box generate`:

```
$ grep -nE 'groupadd|apt-get install' .build/libvirt-order-test/Containerfile
44:    apt-get update && apt-get install -y --no-install-recommends \   <- the box's own packages
64:getent group libvirt >/dev/null 2>&1 || groupadd -r libvirt          <- THIS candy's plan step
72:    apt-get update && apt-get install -y --no-install-recommends \   <- virtualization's packages
```

The prerequisite's `RUN` is **line 64**; `virtualization`'s package install is **line 72**. The ordering the
`require:` edge promises is what the emitter actually produces.

**And the step EXECUTED live, with the failure gone.** `charly box build libvirt-order-test` on that project:

```
$ charly box build libvirt-order-test        # rc=0
$ grep -c 'fatal:' <build log>
0
$ podman run --rm localhost/libvirt-order-test:2026.321.0709 \
    bash -c 'getent group libvirt; dpkg -s libvirt-daemon-system | grep -E "^Status|^Version"'
libvirt:x:999:ubuntu
Status: install ok installed
Version: 12.0.0-1ubuntu5.6
```

Three things that run says at once: the `fatal:` is **gone** (0 lines); the group exists **with `ubuntu` as a
member**, which is the very `usermod -aG libvirt` that used to fail, now succeeding; and
`libvirt-daemon-system` is installed and configured. Before this change the same install emitted the fatal.

**Still not claimed:** the consumer's own `check-ubuntu-debootstrap-vm` in `opencharly/distro-ubuntu`, which
fails on exactly the line this candy prevents. That bed is re-run after the consumer pin bump and reported
